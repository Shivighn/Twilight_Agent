# Fleet Issue Auto-Assignment & WhatsApp Escalation Agent

Build an automated agent that runs **every day at 10:00 AM IST** and manages issue assignment + WhatsApp notifications for fleet managers.

## 1. Objective

Every morning, the agent should:

1. Check the `issues` table for newly triggered/open issues.
2. For every issue having a `vehicle_number`, determine which Fleet Manager (FM) is responsible for that vehicle.
3. Determine the FM by looking at the vehicle's trips from the **last 10 days** in the `trips` table.
4. Get the `fleet_manager_id` mapped to those `service_id`s from the `services_incharge` table.
5. Assign the issue to the appropriate Fleet Manager.
6. Send a WhatsApp group message containing all issues assigned to each FM.
7. Maintain a notification/history table so the same issue is not repeatedly treated as a first-time assignment.
8. Escalate issues if their status remains unchanged:

   * **First notification:** tag assigned Fleet Manager.
   * **After 2 days unchanged:** tag Uday.
   * **After 5 days unchanged:** tag Uday + Siva + Anil.
9. Use the **existing WhatsApp connection/session** that is already running. Do NOT create a new WhatsApp connection or authentication flow.

# 3. Determine Fleet Manager

For every eligible issue:

### Step 1 — Get vehicle

Use:

```text
issues.vehicle_number
```

Example:

```text
TG13T3398
```

### Step 2 — Search trips

Look in `trips` for that vehicle over the **previous 10 calendar days** from the agent execution date.

Use the vehicle number consistently. The system may contain both:

```text
vehicle_number
intrcity_vehicle_no
```

Prefer `vehicle_number`, but make the implementation robust enough to handle the actual existing schema/data.

Only consider relevant trips, preferably trips with valid service IDs.

### Step 3 — Identify the most relevant service

If the vehicle has multiple trips/services during the last 10 days:

* Prefer the **most recent trip**.
* Sort by `departure_datetime DESC`.
* Use that trip's `service_id`.

Example:

```text
Vehicle: TG13T3398

Latest trip:
service_id = 1863
departure_datetime = 2026-08-09 17:15 UTC
```

### Step 4 — Resolve FM

Query:

```text
services_incharge
WHERE service_id = trip.service_id
```

Example:

```text
service_id = 1863
fleet_manager_id = venkyfi
```

The mapping must be data-driven. Do not hardcode vehicle → FM mappings.

# 4. Important Assignment Rules

Only process issues that require action.

Do NOT process:

* Closed issues
* Resolved issues
* Issues that are already fully escalated/handled
* Issues that cannot be mapped to an FM unless they are explicitly placed into an "unmapped issues" handling flow

The exact definition of active/open status should be configurable.

For a new eligible issue:

```text
issues.assignee_id = Fleet Manager's user/staff ID
```

Do not overwrite an existing manual assignee unless explicitly configured to do so.

If an issue already has an assignee, preserve it unless the assignment is specifically owned by this automation.

# 5. Notification Tracking

Create a dedicated table, for example:

```text
fleet_issue_notifications
```

Suggested schema:

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

issue_id UUID NOT NULL,
issue_number INTEGER NOT NULL,

vehicle_number TEXT,

fleet_manager_id TEXT,

first_detected_at TIMESTAMPTZ NOT NULL DEFAULT now(),

last_status TEXT,

last_status_changed_at TIMESTAMPTZ,

fm_notified_at TIMESTAMPTZ,

uday_notified_at TIMESTAMPTZ,

senior_escalation_notified_at TIMESTAMPTZ,

last_notification_type TEXT,

last_notification_at TIMESTAMPTZ,

notification_count INTEGER DEFAULT 0,

created_at TIMESTAMPTZ DEFAULT now(),
updated_at TIMESTAMPTZ DEFAULT now()
```

Add a unique constraint on:

```text
issue_id
```

The table is required to make the agent **idempotent**.

Running the agent twice must not result in duplicate first-time notifications.

# 6. Status Tracking

The escalation timer is based on the issue remaining in the **same status**.

Example:

```text
Day 0:
Issue status = Open
→ Notify FM
```

If status remains:

```text
Open
```

then:

```text
Day 2:
→ Notify Uday
```

If it still remains:

```text
Open
```

then:

```text
Day 5:
→ Notify Uday + Siva + Anil
```

### Important

Do NOT calculate escalation simply from `reported_at`.

Calculate it from the time the issue entered/was last confirmed in its current status.

If the status changes:

```text
Open → In Progress
```

reset the escalation timer for that status.

Example:

```text
Day 0:
Open → FM notified

Day 1:
Open

Day 2:
In Progress
→ reset escalation timer

Day 4:
In Progress

Day 6:
In Progress
→ Uday notification based on 2 days of unchanged In Progress status
```

If possible, maintain a status history table:

```text
fleet_issue_status_history
```

with:

```text
issue_id
status
status_started_at
created_at
```

If an existing issue-status-history mechanism already exists, reuse it instead of creating another table.

3. Include it in the FM's WhatsApp message.


The actual WhatsApp identifiers/group mentions should come from configuration, not be hardcoded throughout the code.

# 11. Daily Processing Algorithm

Implement approximately this flow:

```text
START
  ↓
Run every day at 10:00 AM IST
  ↓
Fetch active/open issues
  ↓
For each issue
  ↓
Check notification tracking
  ↓
Is this a new issue?
  ├── YES
  │    ↓
  │   Find vehicle's trips from last 10 days
  │    ↓
  │   Find most recent relevant trip
  │    ↓
  │   Get service_id
  │    ↓
  │   Find fleet_manager_id from services_incharge
  │    ↓
  │   Assign issue to FM
  │    ↓
  │   Track notification
  │
  └── NO
       ↓
      Compare current status with tracked status
       ↓
      Status changed?
       ├── YES → Reset escalation timer
       └── NO
            ↓
           Check unchanged duration
            ↓
           >= 5 days → Uday + Siva + Anil
            ↓
           >= 2 days → Uday
            ↓
           Otherwise → nothing

  ↓
Group newly assigned issues by FM
  ↓
Send WhatsApp message for Anudeep
  ↓
Send WhatsApp message for Venky
  ↓
Store WhatsApp notification results
  ↓
END
```

# 12. Handling Multiple Trips

A vehicle may have multiple trips within 10 days.

Use:

```sql
ORDER BY departure_datetime DESC
LIMIT 1
```

to determine the most recent service responsible for the vehicle.

However, design the code so this rule can later be changed to:

* majority service
* latest completed trip
* latest active trip
* service frequency

without rewriting the entire agent.

---

# 13. Unmapped Issues

If no trip exists for a vehicle in the last 10 days:

Do NOT randomly assign the issue.

Record it as:

```text
assignment_status = 'unmapped'
```

and log the reason:

```text
No trip found for vehicle in last 10 days
```

Similarly, if a trip exists but `services_incharge` has no FM mapping:

```text
assignment_status = 'unmapped'
reason = 'No fleet manager mapping for service'
```

Create a separate admin/debug notification or log for these cases.

---

# 14. Idempotency

This is critical.

If the agent runs twice:

```text
Issue 7896
```

must NOT result in:

```text
FM notified
FM notified
FM notified
```

Instead:

```text
First run → notification sent
Second run → already notified → skip
```

The same applies to:

* Uday escalation
* Uday + Siva + Anil escalation

Each escalation level should be sent only once per status period.

---

# 15. WhatsApp Failure Handling

If WhatsApp sending fails:

1. Do not mark the notification as successfully sent.
2. Store the failure.
3. Log the WhatsApp error.
4. Retry using a safe retry mechanism.
5. Do not create a duplicate notification if the first request actually succeeded but the response was lost.

Use a notification state such as:

```text
pending
sent
failed
```

with:

```text
attempt_count
last_attempt_at
error_message
```

# 19. Database Safety

Use transactions wherever appropriate.

For a new issue:

```text
resolve FM
→ assign issue
→ create tracking record
```

should be atomic.

Use unique constraints/upserts to protect against concurrent executions.

The agent should be safe even if:

* two instances start simultaneously
* the cron retries
* WhatsApp temporarily fails
* the database connection drops
* the agent crashes halfway through processing

# 20. Implementation Preference

Build this as an independent agent/service that interacts with the existing database and existing WhatsApp connection.

Do not duplicate existing WhatsApp infrastructure.

Suggested logical modules:

```text
issue_agent/
├── scheduler

├── escalation_manager
├── notification_tracker
```
